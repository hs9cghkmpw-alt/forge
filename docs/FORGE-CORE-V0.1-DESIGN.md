# Forge Core v0.1 設計書

**Project:** Forge  
**Status:** REVISED DESIGN / IMPLEMENTATION PENDING  
**更新日:** 2026-09-15  
**対象:** Forge Core（Forgeの最小中核）

---

## 1. この設計書の目的

Forgeの最終目標は、人間が自然な言葉で問題や目的を伝えると、Forgeが意味を理解し、必要な解決方法を考え、実際に使える道具を作り、検証し、会話を通じて改善できる基盤になることである。

最終的にはHardware（ハードウェア）以外の主要ソフトウェア基盤をForge自身が所有する。

この文書ではForge Core v0.1を、単に「動く最小プログラム」としてではなく、**将来のForge全体の品質を支えられる最小の中核**として定義する。

重要な変更点は、既存Forge実装を無条件に再利用もしなければ、無条件に捨てもせず、**品質・責務・Forgeの最終設計への適合性を評価したうえで、流用・再設計・再実装・退役を決める**ことである。

---

## 2. 最重要方針 — 「動く」より「品質」

Forgeでは、次の理由だけで実装を採用してはならない。

- 既に動いている
- テストが通っている
- 既存コードが大量にある
- 過去の実装で使われている

「動く」は必要条件だが、十分条件ではない。

Forgeの採用基準は次の順序とする。

1. **設計品質** — 責務、境界、依存関係、拡張性が適切か
2. **製品品質への寄与** — 将来の高品質アプリを支えられるか
3. **安全性・信頼性** — 失敗を隠さず、検証可能か
4. **理解可能性** — 人間が仕組みを説明・保守できるか
5. **Forge所有化への接続性** — 将来Forge独自実装へ置換・発展できるか
6. **動作・テスト** — 正しく動き、再現可能か

したがって、動作していても品質が基準に達しなければ採用しない。

---

## 3. 既存Forgeに対する基本判断

現在の `forge_ai/core` には、すでに以下のようなForge固有の概念・実装が存在する。

- Domain（問題領域）
- World（問題領域の構造）
- Meaning（入力から抽出した意味）
- Intent（目的・必要概念・操作・制約）
- IR（中間表現）
- Compiler（コンパイラ）
- Logic / Critic / Confirmation 等の補助層

したがって、**新しい `forge_core` パッケージを横に作って、Intent / Entity / State / Actionをもう一度定義することはしない。**

これは既存Coreとの二重化を生み、将来の境界を悪化させるためである。

Forge Core v0.1では、既存実装をいったん棚卸しし、Forgeの真の中核責務を抽出する。

---

## 4. 現時点での既存実装の評価

### 4.1 流用・発展候補

以下は、概念としてForgeの中核へ接続できるため、**原則として残し、品質を確認しながら発展させる候補**とする。

| 現在の要素 | 判定 | 理由 |
|---|---|---|
| `Domain` / `DomainRegistry` | 流用候補 | 問題領域とUIを分離しており、Forgeの意味層に接続できる |
| `World` | 流用候補・再設計 | Actor/Object/Relationship/Ruleをまとめる発想は有用。ただし静的記述と実行時状態の境界を明確化する必要がある |
| `Meaning` / `ExtractedMeaning` | 流用候補・再設計 | 意味理解をCore実行から分離できる。AI依存部分と決定論的部分を明確に分離する必要がある |
| `Intent` | 流用候補・再設計 | 目的・制約・成功条件を表現する方向は有用。ただしAIが生成した結果をそのままCoreの真実にしない |
| `IR` | 強い流用候補・再設計 | 将来のCompiler/Runtimeとの境界として重要。ただし現在の複数IRの責務を整理する必要がある |
| `Logic` | 再設計候補 | 決定論的な意味・ルールを置ける可能性があるが、Runtimeとの責務境界を確認する |
| `Critic` | 上位品質層として流用候補 | Forgeが自分の出力を疑うというCore Constitutionと一致。ただしCoreそのものに混ぜない |
| `Confirmation` | 上位対話層として流用候補 | 不確実性をユーザー確認へ戻す設計に価値がある。ただしCoreの意味モデルとは分離する |
| `Compiler` | 流用候補・大規模再設計 | 既存資産として価値が高いが、Forge Language / Runtimeの最終境界はまだ確定していない |

### 4.2 そのままCoreへ持ち込まないもの

以下は、現在動作していてもForge Core v0.1の責務には直接入れない。

- LLM Providerそのもの
- Prompt構築
- UI / Flutter固有処理
- HTTP / API固有処理
- Supabase等の外部データ基盤固有処理
- 生成アプリ固有の処理
- 自律Agentの実行制御
- 実機E2E（End-to-End：端から端までの統合試験）固有処理

これらは必要な上位層・開発基盤として利用してよいが、Coreの意味論を汚染させない。

### 4.3 再実装が必要になる可能性が高い領域

以下は最終的にForge自身で所有すべき中核として、既存実装をそのまま最終形とは扱わない。

- Coreの正式な型体系
- Coreの状態モデル
- CoreのAction / Operation意味論
- Coreのエラー体系
- Coreの検証規則
- CoreとRuntimeの境界
- Forge Languageとの境界
- IRの正式な安定仕様
- CoreからRuntimeへ渡す実行契約

これらは既存コードから知見を吸収しつつ、品質基準に合わせて再設計・再実装する。

## 5. 改訂後のCore概念

v0.1では、以前の単純な

`Intent / Entity / State / Action`

をそのまま最終Coreモデルにはしない。

まず以下の責務を分離して扱う。

```text
Human Intent
    ↓
Meaning
    ↓
Domain / World
    ↓
Intent
    ↓
Core IR（中間表現）
    ↓
Validation
    ↓
Execution Contract（実行契約）
    ↓
Observable Result
    ↓
Evidence（検証証拠）
```

重要なのは、**AIが出した意味と、Coreが保証する事実を同一視しないこと**である。

AIは候補を生成できる。Coreは検証された構造だけを実行対象として受け入れる。

---

## 6. Core v0.1の責務

### Coreが担当する

- Core内部モデルの定義
- 構造の妥当性検証
- 型・参照・制約の検証
- 決定論的な状態遷移
- 実行可能な操作の評価
- エラーの明示
- 実行結果の観測可能化
- 再現可能性
- 検証証拠の生成

### Coreが担当しない

- 自然言語理解そのもの
- LLM推論
- UI描画
- ネットワーク
- データベース
- OS機能
- 最終的なコード生成
- AI学習
- ユーザーとの会話制御

これらはCoreの外側に置く。

---

## 7. AIをCoreから分離する理由

Core v0.1の最初の検証ではAIを使用しない。

固定した人間作成の入力をCoreへ渡し、次を検証する。

```text
固定入力
 ↓
Core Model
 ↓
Validation
 ↓
Deterministic Execution（決定論的実行）
 ↓
Result
 ↓
Evidence
```

これにより、失敗時に

- 入力が悪い
- モデルが悪い
- 検証が悪い
- 実行が悪い

を分離できる。

AIは後からMeaning / Intent生成側へ接続する。

---

## 8. v0.1で最初に実装するもの

巨大なFramework（フレームワーク）を作らない。

ただし、単なる買い物リストのサンプル実装にもならない。

最初に実装するのは、**Coreの品質特性を測れる最小の決定論的実行核**とする。

```text
Core Value Objects（値オブジェクト）
    ↓
Core Schema / Type Rules
    ↓
Validator
    ↓
State Transition
    ↓
Result / Error
    ↓
Evidence
```

買い物リストは、この核を検証する一つのテストケースとして使用する。

Core自身が「買い物リスト」を知っている設計にはしない。

## 9. 品質ゲート

Core v0.1は「テストが通った」だけでは完了としない。

### Gate A — 設計品質

- 責務が一つずつ明確である
- 同じ概念を複数箇所で定義していない
- CoreとAI/UI/Runtimeの境界が説明できる
- 将来の拡張で破綻しにくい

### Gate B — 正確性

- 正常系を処理できる
- 不正入力を拒否できる
- エラーが明示される
- 同じ入力に対して同じ結果になる
- 状態遷移が検証できる

### Gate C — 品質・安全性

- データ破壊や不正状態を防げる
- 暗黙の成功を作らない
- 未検証データを実行しない
- 将来の権限・安全性拡張を阻害しない

### Gate D — 保守性

- 実装者が各処理を説明できる
- テストが仕様を表している
- 依存関係が追跡できる
- 変更理由をGitHubで追跡できる

### Gate E — Forge適合性

- Forgeの最終設計へ接続できる
- 外部ソフトウェアを最終Coreの必須条件にしない
- Forge独自実装へ段階的に置換できる
- 高品質な生成アプリを支える基礎になる

## 10. 既存実装の扱い方

既存コードは次の4分類で管理する。

```text
A: REUSE
   品質を満たす。流用・発展する。

B: REBUILD
   発想・知見は有用だが、設計または実装を作り直す。

C: REFERENCE
   学習・比較・検証資料として残す。

D: RETIRE
   Forgeの最終設計に不要。新しい実装から依存しない。
```

この分類は「動く / 動かない」ではなく、Forgeの品質基準で決める。

## 11. 現在の実装から得るべきもの

現在の `forge_ai/core` は捨てる対象ではない。

むしろ、これまでの開発で得られた以下の知見をForgeの設計材料として回収する。

- 後方互換性を壊さずに概念を追加する方法
- DomainとUIを分離する方法
- AI Providerを差し替える境界
- World / Meaning / Intentの責務分離
- IRを使ってAIと実装を接続する方法
- Compilerへ接続するための既存知見
- Critic / Confirmationによる品質・不確実性の扱い
- 実機・生成アプリ・修復・検証で得られた失敗事例

ただし、これらを最終設計として無条件に固定しない。

**過去の実装はForgeの経験値であり、最終仕様ではない。**

## 12. 開発方式

ユーザーが手を動かして理解することを前提とする。

```text
設計
 ↓
ユーザーが実装
 ↓
実行
 ↓
テスト
 ↓
失敗・問題を記録
 ↓
原因を理解
 ↓
修正
 ↓
再テスト
 ↓
品質レビュー
 ↓
GitHubへcommit / push
 ↓
次の最小単位
```

AIは設計レビュー・調査・デバッグ・ドキュメント化を支援するが、重要な仕組みをブラックボックスのまま残さない。

## 13. v0.1の完了条件

次のすべてを満たすこと。

1. Coreの責務境界を説明できる。
2. Core内に重複した意味モデルが存在しない。
3. 構造化入力を検証できる。
4. 決定論的な状態遷移を実行できる。
5. 不正状態を拒否できる。
6. 結果とエラーを観測できる。
7. Evidence（検証証拠）を残せる。
8. テストで仕様を固定できる。
9. AIなしでCore単体を検証できる。
10. 既存Forgeとの関係を説明できる。
11. 将来のRuntime / Language / OSへ接続する境界を壊していない。
12. 実装者がコードの意味を説明できる。
13. GitHubに設計・実装・テスト結果が記録されている。
