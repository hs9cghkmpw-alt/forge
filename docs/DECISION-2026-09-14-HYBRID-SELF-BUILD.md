# Forge 方針決定記録 — ハイブリッド自給化・長期開発方針

**決定日:** 2026-09-14  
**対象:** Forge プロジェクト  
**状態:** 採用（長期方針）

---

## 1. 今回の最重要決定

Forge は **ハイブリッド方式**で長期的に開発する。

ここでいうハイブリッドとは、最初からすべてを自作するのではなく、既存のOS・ライブラリ・ツール・ハードウェア等を利用して開発・学習を進めながら、Forgeの中核部分を段階的に自作し、最終的な自給度を高めていく方式を指す。

また、「Forgeで作る」という表現ではなく、**ユーザー自身が実際に手を打ってコードを書き、Forgeそのものを作っていく**ことを開発体験の中心にする。

これは完成まで長期間かかることを前提としたプロジェクトである。

---

## 2. 開発の基本思想

### 2.1 学習と実装を分離しない

Forgeは単に完成品を作るためのプロジェクトではない。

実際にコードを書き、動かし、壊し、調査し、修正することを通して、以下を含むコンピュータシステムの仕組みを理解することも目的とする。

- OS（Operating System：コンピュータ全体を管理する基本ソフト）
- Kernel（カーネル：OSの中核）
- Driver（ドライバ：ハードウェアをOSから扱うためのソフト）
- Filesystem（ファイルシステム：データを保存・管理する仕組み）
- Network Stack（ネットワークスタック：通信処理の階層構造）
- Security Model（セキュリティモデル：権限・隔離・安全性の仕組み）
- Graphics（グラフィックス：画面表示・描画の仕組み）
- Runtime（ランタイム：プログラムを実行する基盤）
- Compiler（コンパイラ：プログラムを実行可能な形へ変換するソフト）
- Standard Library（標準ライブラリ：言語に標準で提供する基本機能群）
- Package System（パッケージシステム：機能を配布・再利用する仕組み）
- AI / Tensor Engine（AI計算・テンソル演算の基盤）

---

## 3. 「自作」の意味

「全部を今すぐゼロから自作する」という意味ではない。

段階を分ける。

1. 既存技術を利用して動くものを作る
2. 仕組みを理解する
3. Forge独自の抽象化・実装へ置き換える
4. Forge自身の実装範囲を広げる
5. 必要に応じて低レイヤーまで降りる
6. 最終的にForge自身が自分の実行基盤として機能できる範囲を増やす

したがって、外部技術を利用すること自体は方針違反ではない。

**外部依存を使う → 理解する → Forge側へ段階的に移す**、という流れを基本とする。

---

## 4. ハードウェアについて

既存ハードウェアは外部に残す。

当面はPC等の既存ハードウェア上でForgeを動かし、その上のソフトウェア層をForge側で段階的に自作していく。

つまり、最初からCPUやメモリなどの物理ハードウェアまで自作することを目標にはしない。

---

## 5. 将来的なForgeの層

長期的には、少なくとも次のような層を対象として設計・実装を進める。

### Forge OS

- Kernel
- Driver Layer（ドライバ層）
- Filesystem
- Network Stack
- Security Model
- Graphics
- Process / Memory Management（プロセス・メモリ管理）
- Device / I/O Management（デバイス・入出力管理）

### Forge Runtime

- Forge Language（Forge独自言語）
- Compiler
- Standard Library
- Package System
- App Runtime
- Forge Document / UI実行基盤

### Forge AI

- AI基盤
- Tensor Engine
- 推論・生成基盤
- AIとの安全な実行境界
- 必要能力の生成・再利用・検証

### Forge Apps

- Forge Runtime上で動くアプリケーション
- ユーザー要求から能力を組み合わせて構築されるアプリ
- 必要に応じた再利用可能な能力・部品

※ これは長期的な対象範囲であり、現時点ですべて実装済みという意味ではない。

---

## 6. 現在のForgeとの関係

現在のForgeは、Flutter / Material 3 / Riverpod、FastAPI、Supabase、GitHub等の既存技術を利用したアプリ生成基盤から開始している。

現行のJSON UI / Forge Document / Runtime設計は捨てず、これを**現在の実験・実装基盤**として利用する。

その上で、将来的に必要な部分をForge独自のRuntime・Language・OS等へ段階的に置き換えていく。

したがって、現在の実装と将来の自作基盤は対立しない。

**現在のForgeを土台として、Forge自身の基盤を育てる。**

---

## 7. 実装の進め方

基本ループは以下とする。

```text
設計
  ↓
自分でコードを書く
  ↓
実行する
  ↓
実機・テスト環境で確認する
  ↓
問題を調査する
  ↓
修正する
  ↓
テストする
  ↓
GitHubへ記録する
  ↓
次の層へ進む
```

AIは設計補助、調査、レビュー、デバッグ支援、文書化等に利用する。

ただし、**「AIが作ったから完成」にはしない。**

ユーザー自身が仕組みを理解し、実際に動作確認できることを重視する。

---

## 8. GitHubを長期記録として扱う

ForgeのGitHubリポジトリを、単なるソースコード置き場ではなく、**プロジェクトの長期記録・再開地点・設計台帳**として扱う。

以下を継続的に記録する。

- 決定事項
- 設計変更
- 実装状況
- 実機テスト結果
- 失敗と原因
- 解決方法
- 次回の再開地点
- AIへの申し送り
- マイルストーン

これにより、別PCからでも、別のAIや協力者でも、GitHubを見れば途中から再開できる状態を目指す。

---

## 9. 検証方針

実装したものは、可能な範囲で実機・テスト環境で確認する。

既存方針に従い、マイルストーン完了時には標準検証を重視する。

例：

- Python Test
- flutter analyze
- flutter test
- flutter build web
- 必要に応じて実際の起動確認

低レイヤー実装へ進んだ場合は、その層に対応したテスト・実機検証へ拡張する。

---

## 10. 長期プロジェクトとしての原則

### 原則A — 急いで完成させない

数年単位になっても構わない。

### 原則B — 動く最小単位を積み上げる

大きな機能を一度に作らず、理解可能な単位で実装する。

### 原則C — 既存技術を敵視しない

既存技術は学習・比較・ブートストラップ（立ち上げのための土台）として積極的に利用する。

### 原則D — 依存関係を把握する

外部ライブラリやサービスを使う場合、それがForgeのどの層に依存しているのかを記録する。

### 原則E — 徐々に自給化する

「外部に頼っている部分」を一覧化し、必要性と優先度を見ながらForge側へ置き換える。

### 原則F — 理解できないものをブラックボックスにしない

AIや既存ライブラリを使う場合でも、重要な仕組みは学習対象として扱う。

### 原則G — GitHubに残す

チャットだけに重要な情報を残さない。長期的に必要な判断・仕様・実験結果はMD等に記録する。

---

## 11. 今回の決定を一文で表すと

> **Forgeは、既存技術を土台として使いながら、ユーザー自身が手を動かして学習・実装・検証を繰り返し、時間をかけてForge自身のOS・Runtime・Language・AI等を自作し、自給度を高めていくハイブリッド型の長期プロジェクトとして進める。**

---

## 12. 次回の再開地点

次は、この方針を前提として、Forge全体を構成する**「何を作るのか」の完全な一覧（全レイヤー・全主要コンポーネント）**を確定し、依存関係と実装順序を設計する。

その後、最初に手を付ける最小実装単位を決める。
