# Forge 手作り開発・最終設計方針書

**Project:** Forge  
**Repository:** `hs9cghkmpw-alt/forge`  
**Status:** 長期開発・基盤設計フェーズ  
**最上位方針:** 手作りで理解しながら、自分たちで所有できるアプリ生成基盤を作る

## 1. Forgeとは何か

Forgeは、人間が自然言語で「こういうアプリを作りたい」と指示すると、その要求を理解・設計し、実際に高品質なアプリとして形にできる開発基盤を目指す。

単なるAIコード生成サービスではない。最終的には、アプリを作るための仕組みそのものをForgeが持つことを目標とする。

## 2. 最終ゴール

最終形は概念的に次の構造とする。

```text
Forge Apps
    ↓
Forge UI
    ↓
Forge AI
    ↓
Forge Runtime
    ↓
Forge OS
    ↓
Hardware
```

原則としてHardware（ハードウェア）だけは外部に残し、それより上の主要ソフトウェア基盤は時間をかけてもForge側で自作・所有・管理できる状態を目指す。

## 3. Forgeで作られるアプリの品質方針

Forgeが生成するアプリは「AIがそれっぽいものを作った」レベルを目標にしない。実際に人が使う製品として成立する品質を目指す。

最終的には、アプリストアで上位を狙えるレベルの完成度を品質目標として置く。

品質評価には、機能品質、UI品質、UX品質、性能、安定性、セキュリティ、保守性を含める。

## 4. AI生成と品質保証を分離する

「AIが生成した＝完成」としない。

```text
ユーザー要求 → AI理解 → アプリ設計 → 構造化仕様 → 生成 → 検証 → 修正 → テスト → 品質評価 → 完成
```

Forge自身が生成物を評価し、必要に応じて修正できる仕組みを持つ。

## 5. 手作り開発方針

Forgeそのものの開発では、効率だけを最優先しない。自分で手を動かして理解すること自体をForge開発の目的とする。

```text
設計 → 自分でコードを書く → 実行 → エラー確認 → 原因理解 → 修正 → 再実行 → 動作確認 → 記録
```

AIは調査、説明、エラー解析、設計レビュー、比較、テスト案、学習補助などに利用できる。ただしForgeの基礎部分については、自分でコードを書き、実行し、理解することを優先する。

## 6. ハイブリッド開発

すべてを一気に自作せず、段階的に既存技術からForge独自基盤へ移行する。

```text
既存技術 → Forgeとの統合 → Forge独自実装 → Forgeによる自給
```

## 7. Forge OS

最終的にはOSレベルまで自作する。対象例：Kernel（OSの中核）、Driver Layer（ハードウェア制御層）、Filesystem（ファイル管理）、Network Stack（通信機能）、Security Model（権限・安全性の仕組み）、Graphics（画面描画）、Process / Thread管理、Memory管理、Device管理。

最初から全部作らず、学習可能な単位に分割して一つずつ実装する。

## 8. Forge Runtime

Forge OS上で動く独自実行基盤。

- Forge Language
- Compiler（プログラムを実行可能形式へ変換する仕組み）
- Standard Library（基本機能の集合）
- Package System（部品・ライブラリ管理）
- App Runtime（アプリ実行環境）

## 9. Forge AI

ForgeのAI部分も独立した基盤として設計する。

- Tensor Engine（AI計算基盤）
- Model Runtime
- Tokenizer
- Inference Engine（AI推論処理）
- Agent System（AIが複数の処理を組み合わせる仕組み）
- Context / Memory
- Tool Calling
- App Generation Logic
- App Evaluation

目標は「AIがコードを書く」だけでなく、「AIがアプリを理解して設計・生成・検証する」ことである。

## 10. Forge UI

Forgeが生成するアプリの品質を決める重要な層。UIを単なる部品集として扱わない。

```text
要求 → 情報設計 → 画面構成 → 操作設計 → デザイン → 実装 → UX評価
```

## 11. Forge Apps

Forgeへの自然言語要求を起点として、要求理解、要件定義、仕様化、UI設計、データ設計、ロジック設計、生成、テスト、品質評価、修正、完成までを一貫して処理する。

## 12. JSONを中心にする方針

AIから直接大量のコードを吐かせるのではなく、AI → 構造化された仕様 → 実装という方向を基本とする。AIはJSONなどの構造化された情報を生成し、実際のコード生成・実行はForge側が担当する。

## 14. Forge憲法

1. Forgeは単なるAIコード生成ツールではない。
2. 最終的にはForge自身が主要なソフトウェア基盤を所有する。
3. 開発者自身が手を動かして理解する。
4. AIによるブラックボックス化を避ける。
5. Forgeが作るアプリの品質を妥協しない。
6. 「動けば完成」ではない。
7. 品質・UX・安全性・保守性まで含めて製品とする。
8. ハイブリッド方式で段階的に自給化する。

## 15. 開発ルート

アプリ先行と基盤先行のどちらか一方に固定せず、ハイブリッドで進める。

```text
アプリを作って成果を出す
        ↕
基盤を手作りして理解する
        ↓
Forge独自基盤へ置換
        ↓
最終的な自給化
```

## 16. 最大の注意点

最も避けるべきなのは、「Forgeを作るためにForge自身にコードを書かせ始め、作っている本人が何も分からなくなる」ことである。

Forgeの自動化能力を高めることと、Forge開発者が理解することを別々の目標として管理する。

## 17. 完成の定義

### Phase 1
Forgeでアプリを構造化して生成できる。

### Phase 2
生成アプリの品質を自動評価できる。

### Phase 3
Forge独自Runtimeでアプリを実行できる。

### Phase 4
Forge AIが設計・生成・検証まで行える。

### Phase 5
Forge OS上でForge Runtimeが動く。

### Phase 6
Forge自身が主要基盤を自給できる。

### Final
Hardware以外の主要ソフトウェア基盤をForgeが所有し、その上で高品質なアプリを生み出せる。

## 18. この文書の位置付け

この文書は、今後の実装で迷ったときの上位設計（最も優先される設計方針）とする。

個別の技術選定が変更されても、Forgeの最終目的、品質基準、手作り開発、自給化方針は変更しない。
