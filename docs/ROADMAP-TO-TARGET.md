2026-08-14 / 起点: CEO提示の完成図（AI-NATIVE APP BUILDER）

このファイルは `docs/ROADMAP.md`（全体の方針）を、**提示された完成図を

## 0. 先に言うべきこと

**完成図は1つの製品ではなく、3つが積み重なっている。**

| # | 何 | 完成図での見え方 | 今の状態 |
|---|---|---|---|
| A | **生成物の質** | スマホ3画面（家計簿・ジャーナル・タスク） | 一本道は動くが、**見た目が届いていない** |
| B | **作る体験** | Web IDE（チャット／設計／データ／スタイル／設定＋ライブプレビュー） | **器が違う**（Forgeは今Flutterアプリ1画面） |
| C | **出す** | プレビュー／コード／公開する | **未着手** |

この3つは**コストも価値も別物**である。まとめて「完成図」と呼ぶと、
どれから手を付けるかが決められない。以下は3つを分けて扱う。

**結論を先に**: Aから始めるべきである。理由は §4。

## 1. 現状の底（実測、2026-08-14）

推測ではなく実コードで確認した値。

```
Widget          19種（v1.9）
                bar_chart, button, card, checkbox, checklist, choice_field,
                column, date_field, divider, form, heading, list,
                record_list_view, row, section_header, slider, tab_view,
                text, text_field

                spacing_scale（size→数値）

                  / タイポグラフィ指定無し / 影・境界線の指定無し

グラフ          bar_chart のみ（v1.9で group_by / aggregate 対応）

```

`color_scheme` が**自由なmap**である点は重要である。役割名を増やすのに
Schema変更が要らない。使う側（Widget）が読めるかどうかだけが問題になる。

## 2. 完成図の分解

完成図のスマホ3画面を、**必要なものの種類ごとに**分けた。
「何が足りないかを種類ごとに言える」という Forge の方針
（`FORGE-SELF-EXTENSION-ARCH-REVIEW-v2.md`）に沿う。

### 2-1. 既存19 Widgetで**今日でも描けるもの**

| 完成図の要素 | 使うもの |
|---|---|
| 「今月の概要 ¥243,800」の大きな数値 | `card` + `heading` + `text` |
| 「前月比 +¥28,400 (13.2%)」 | `text`（色は`design_tokens`次第） |
| タスク一覧のチェック行 | `checklist` / `record_list_view` |
| セクション見出し | `section_header` |
| 「書き始める」ボタン | `button` |
| 今日/今週/すべて の切替 | `tab_view` |

**つまり、完成図の骨格の相当部分は既に描ける。** 届いていないのは
主に**装飾と情報密度**である。ここが §4 で P0 を最優先にする根拠になる。

### 2-2. 新しい Widget が要るもの

| 要素 | 何が要るか | 大きさ | 使う画面 |
|---|---|---|---|
| ドーナツ / リング（70%・75%） | `donut_chart` | 中 | 家計簿・タスク |
| 行内の細い進捗バー | `progress_bar` | **小** | 家計簿・タスク |
| カテゴリのアイコン、絵文字 | `icon` | **小** | 全画面 |
| 下部ナビゲーション | `bottom_navigation`（`tab_view`の兄弟） | 中 | 全画面 |
| 丸い＋ボタン | `fab`（`button`の変種でも可） | **小** | 家計簿・タスク |
| ヒーロー画像 | `image` + `data.image` | 大 | ジャーナル |
| カレンダー | `calendar` + `view.calendar` | 大 | ジャーナル |
| 気分の絵文字選択 | `choice_field` の表示変種 | 小 | ジャーナル |
| 行の左アイコン＋右バッジ | `list` / `record_list_view` の拡張 | 中 | 全画面 |

**小さいものが4つある**（`progress_bar` / `icon` / `fab` / 絵文字選択）。
この4つだけで完成図の情報密度はかなり近づく。

### 2-3. Widget ではなく**見た目の言語**が要るもの

これが一番効くのに、一番見落とされやすい。

| 要素 | 今 | 要るもの |
|---|---|---|
| 全体の暗い背景・カード階層 | primary色1つ | `surface` / `background` / `on_*` の役割セット |
| 収入=緑 / 支出=赤 | 無し | **意味の色**（positive / negative / warning） |
| グラデーション | 無し | `gradient` トークン |
| 文字の大小・太さの秩序 | 無し | `typography_scale` |
| 影・境界線 | 無し | `elevation` / `border` |
| ライト/ダーク | 無し | `color_mode` |

**Widget を1つも足さずに、ここだけで印象は大きく変わる。**
`color_scheme` が自由mapなので、Schema変更の負担も小さい。

## 3. 見落としてはいけない罠 — 「作れたふり」

**Widget を実装しても、会話からは到達しない。**

Forge は能力を5段階で数える（`FORGE-SELF-EXTENSION-ARCH-REVIEW-v2.md` §56）:

```
表現できる → 検証できる → コンパイルできる → 描画できる → 使える
```

`transform.aggregate` で**既に踏んでいる**。

* Runtime 実装済み（`frontend/lib/json_ui/runtime/forge_aggregate.dart`）
* Validator 対応済み（v1.9）
* **しかし Compiler が `group_by` / `aggregate` を1度も出力しない**
  （`grep -rn "group_by" forge_ai/` が **0件**）

結果、**会話からは一度も使われていない**。手書きのForge Documentを
`/update` で渡せば描画されるが、それは製品としては届いていない。

したがって、このロードマップでは
**「Widget追加」と「Compiler接続」を必ず対にする**。
片方だけ終わった状態を「完了」と数えない。

さらに言えば、Compilerが出力できるようになっても、**Cognitive Pipelineが
「ここはドーナツが良い」と判断しなければ**完成図にはならない。
Widget追加は5段階のうち2段階目までで、残り3段階が本体である。

## 4. 進める順序

### P0. 見た目の言語を整える（Widget追加 0個）

**最初にやる。最も安く、最も効く。**

* `design_tokens` を拡張: 意味の色 / surface / typography / elevation /
  gradient / color_mode
* Cognitive Pipeline が**アプリの性格に合わせてトークンを選ぶ**
  （家計簿=落ち着いた寒色 / ジャーナル=柔らかい暖色 / タスク=明快）
* Design Critic に「トークンが選ばれているか」の軸を足す

**この時点で見えるようになるもの**: 完成図の「洗練された感じ」の
かなりの部分。Widget が19種のままでも、色と余白と文字の秩序が
決まれば別物に見える。

**なぜ最初か**: Widget を先に足しても、色が1色のままなら
完成図には近づかない。逆にトークンが決まっていれば、後から足す
Widget は**自動的に馴染む**。順序が逆だと作り直しになる。

### P1. 小さい Widget 4つ（+ Compiler接続）

`progress_bar` / `icon` / `fab` / 絵文字選択

* いずれも描画は単純。**Compiler接続の方が本体**
* この4つで完成図の情報密度に近づく

**この時点で見えるようになるもの**: カテゴリ別支出の行、
タスクの進捗、＋ボタン。完成図の「実用アプリらしさ」。

### P2. ドーナツ / リング（+ Compiler接続）

`donut_chart`

* `transform.aggregate` が**既にある**ので、データ側は揃っている
* **ここで aggregate が初めて会話から使われる**（P2の副産物として
  aggregate の Compiler接続を済ませる）

**この時点で見えるようになるもの**: 完成図の一番目を引く部分。

### P3. 下部ナビゲーション + 行の拡張

`bottom_navigation` / `list` の leading・trailing

* 「1画面のアプリ」から「複数画面のアプリ」へ変わる
* 生成物の**規模**が一段上がる

### P4. 画像とカレンダー

`image` + `data.image` / `calendar` + `view.calendar`

* **ここだけ性質が違う**。画像は保存・配信・生成の3つが要り、
  カレンダーは新しい描画そのものが要る
* ジャーナル系アプリの完成度に効くが、P0〜P3より重い

### P5. Web IDE（＝ B の製品）

チャット／設計／データ／スタイル／設定 + ライブプレビュー

* **別の器**である。今のFlutterアプリへの機能追加ではない
* ライブプレビューは、生成中のForge Documentを逐次描画する仕組みが要る
* 「コード」表示は Forge Language JSON を見せるだけなら軽いが、
  Dart/TS コード書き出しなら重い

### P6. 公開 / API連携（＝ C の製品）

* 公開 = 生成物をどこかへ置いて他人が開ける状態にする
* API連携 = 生成アプリが外部サービスを叩けるようにする（**新しい
  安全性の問題が発生する**。鍵の扱い・送信先の制御）

## 5. 完成図の数字について

完成図のフッターに「コンポーネント 128 / API連携 6 / データモデル 12 /
セキュリティ✓」とある。

**この数字を目標として扱わないこと**を提案する。

* 「コンポーネント128」は、19種のWidgetから128種へ増やすという意味なら
  **方向が違う**。完成図の3画面は、上で分解したとおり**10種前後の追加**で
  描ける。128という数は、Widgetではなく「配置されたUI要素の個数」を
  数えている可能性が高い
* Widget種類を増やすほど、Compiler・Validator・Runtime の3者を揃える
  負担が増える（TD37 で実際に踏んだ）。**種類を増やすより、
  少ない種類を良い見た目で組み合わせる方が近道である**

数字そのものが目標になると、「128種あるが会話からは使えない」という
状態が正当化される。§3 の罠と同じ形である。
