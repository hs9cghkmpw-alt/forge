# Metric Semantics V1 — 数値が「どういう量か」

**2026-08-17 / FORGE-R1-CLOSURE-015 §2**
**実装: `forge_ai/core/ir/ir_types.py` (`MeasureSemantics`)**

---

## 1. なぜ必要だったか

Hero KPI（v1.11）の最初の実装は「Entityの最初のNUMBER Fieldを合計する」
だった。その結果、**本番経路で実際にこれが生成されていた**。

```
読書記録  rating(評価5段階) → 評価の合計
釣果記録  size(サイズcm)   → 魚のサイズの合計
```

どちらも意味を成さない。「評価の合計が42」は何も言っていないし、
「今まで釣った魚の長さの合計」は誰も知りたくない。

原因ははっきりしている。

> **「数値である」ことと「足すと意味のある量である」ことは別**

型（`FieldType.NUMBER`）は前者しか言っていないのに、後者を推測していた。
分からないものを「合計できる」という**楽観側へ倒していた**
（`CLAUDE.md` §3）。

---

## 2. 語彙

| 値 | 意味 | 例 | 最初に知りたいこと |
|---|---|---|---|
| `additive` | 足し合わせに意味がある | 金額・数量・歩数・距離 | **合計** |
| `averageable` | 平均に意味がある。合計は無意味 | 評価・点数・満足度 | **平均** |
| `level` | ある時点の水準 | 体温・体重・残高 | **最新値** |
| `extremum` | 最大/最小に意味がある | 魚のサイズ・自己ベスト | **最大** |
| `identifier` | 集計しない数値 | 年号・部屋番号 | — |
| `unknown` | **既定値。** 分からない | — | — |

---

## 3. 集計方法ではなく「量の性質」を持つ

`preferred_aggregate`（sum/avg/…）だけを持たせる案もあったが、
**なぜそう集計するのかが失われる**。

「合計する」は結論であって、理由は「足し合わせに意味がある量だから」
である。理由を持っておくと、後から別の問いにも答えられる——
「この数値をグラフのY軸にしてよいか」「前月比を出してよいか」は、
集計方法ではなく量の性質から決まる。

だから**性質と集計を分けて**、性質から集計を引く。

```python
preferred_aggregate(MeasureSemantics.AVERAGEABLE)  # "average"
preferred_aggregate(MeasureSemantics.UNKNOWN)      # None → Hero KPIを出さない
```

---

## 4. 分からないときに出さない

`unknown` と `identifier` は **`None`** を返し、Hero KPIは作られない。

「出せるから出す」をすると、意味の無い数値が画面で一番大きくなる。
それは**何も無いより悪い**——利用者はそれを事実だと読む。

`unknown` を `additive` へ倒した瞬間に、上の2件（評価の合計・サイズの
合計）が復活する。だから既定値は `unknown` である。

---

## 5. 誰が決めるか

| 経路 | 決める人 |
|---|---|
| Curated Domain | 人手（`ir_generator.py`の定義表） |
| AI合成 | **AI**（閉じた6択から選ぶ） |
| 未指定・不正な値 | `unknown`（＝KPIを作らない） |

AIには自由記述させない。Design Roleと同じ理由である——Forgeが保証
できない値が入らず、**選ばれなかった候補が分かる**。

Promptには「**迷ったらunknownにすること**」と明記してある。分からない
のにadditiveと答えると、足しても意味の無い数値が画面で一番大きく
表示される、という理由も添えてある。

## 6. お金の出入り（`MonetaryFlow`）

`additive` だけでは足りない場面がある。**金額を全部足したものは残高では
ない**——収入と支出を区別していないからである。

```python
MonetaryFlow(
    amount_field="amount",       # 金額を持つField
    direction_field="entry_type", # 収支の別を表すCHOICE Field
    outflow_value="支出",         # そのうち「出ていく」を意味する値
)
```

Entity側に置いたのは、これが**3つのFieldにまたがる関係**だからである。
1つのFieldの属性にすると、残り2つとの繋がりが暗黙になる。

`outflow_value` をIRが持つのが要点である。「支出」という語をCompilerが
知っていると、英語のDomainや別の言い回し（「出金」）に対応できない。
**意味はIRが持ち、Compilerはそれを読むだけ**にする（ADR-012）。

これによりCompilerは、収入・支出・残高の3つを別々に出せる。

```
残高    metric.primary    収入 − 支出   ← 画面で一番大きい
収入    finance.income    収入だけの合計
支出    finance.expense   支出だけの合計
```

---

## 7. 増やすときの条件

語彙を無制限に増やさない。増やす前に:

* 既存の6つの組み合わせで表現できないか
* その性質から、**画面に出す集計が一意に決まるか**

決まらないものを足すと、「性質は分かったが何を出せばいいか分からない」
という、使えない語彙が増える。
